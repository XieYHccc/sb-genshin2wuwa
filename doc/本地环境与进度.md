## 4. 实测（RTX 3090 Ti 电脑，2026-11-13）

测试脚本是一次性的，没有放进仓库。条件：torch 2.11.0+cu128，batch 1，开启 TF32 和 cudnn.benchmark。

**矩阵乘（8192³）**：tf32 37.1 TFLOPS，bf16 75.7，fp16 74.6。3090 Ti 的 bf16 理论峰值约 80。

**DC-AE f32c32-sana-1.1 编解码（ms）**：

| 分辨率 | 精度 | 编码 | 解码 | 合计 |
|---|---|---|---|---|
| 1024×576 | fp32 | 131 | 214 | 345 |
| 1024×576 | bf16 | 80 | 120 | 200 |
| 1024×576 | fp16 | 79 | 120 | 199 |
| 512×512 | fp32 / fp16 | 60 / 37 | 96 / 54 | 157 / 91 |
| 1280×704 | fp32 / fp16 | 196 / 119 | 326 / 184 | 522 / 303 |
| 1920×1088 | fp32 / fp16 | 451 / 278 | 760 / 442 | 1211 / 720 |

- channels_last 没有收益：1024×576、fp16 下合计 202 ms
- 和 fp32 的输出相比，bf16 约 57.5 dB PSNR，fp16 约 75.8 dB；都没有 NaN。测试用的是合成图
- encoder 153.0M、decoder 159.2M 参数；scaling_factor 为 0.41407；1024×576 的 latent 形状是 (1, 32, 18, 32)

**DiT-B 体量的 Transformer**：12 层，d=768，12 个头，没有 adaLN，85M 参数。DiT-B 的 adaLN 调制计算量可以忽略。

| 项目 | 结果 |
|---|---|
| 推理，576 token，batch 1，bf16 | 3.56 ms |
| 推理，576 token，batch 2（正反两个场），bf16 / fp16 | 6.11 / 5.70 ms |
| 训练一步，256 token × batch 128，bf16 + AdamW | 399 ms，峰值显存 13.0 GiB；15 万步约 16.6 小时 |

**实际的 DiT（2026-11-14，`train.py --bench`）**：带 adaLN、2D RoPE、QK-norm，含每步的 OT 配对、EMA 更新和梯度裁剪；batch 128 × 256 token，bf16 autocast，没开 torch.compile。

| 模型 | 参数 | 每步 | 峰值显存 | 2.5 万步 | 15 万步 |
|---|---|---|---|---|---|
| DiT-S（hidden 384，12 层，6 头） | 32.5M（adaLN 10.9M） | 202 ms | 8.6 GiB | 1.4 小时 | 8.4 小时 |
| DiT-B（hidden 768，12 层，12 头） | 129.6M（adaLN 43.7M） | 506 ms | 18.2 GiB | 3.5 小时 | 21.1 小时 |

DiT-B 比上表那个"没有 adaLN 的 85M Transformer"慢约 27%、显存多约 5 GiB，主要是 autocast 下 LayerNorm 和 adaLN 调制在 fp32 里做，残差流的激活是 fp32。都不含评估面板的时间。

### 5.2 阶段 0：AE 平移等变测试（plan §8.2）

新写 `ae_shift_test.py`。每个游戏取 s00 的 8 帧（鸣潮 s00 是傍晚，对测 AE 本身没有影响），规范分辨率下取比整帧窄 32 像素的窗口，平移 k = 1…32 像素后分别做 AE 重建，在公共区域（去掉离窗口边界 32 像素以内）和 k=0 的重建比 PSNR。

```bash
python ae_shift_test.py --images data/10_frames/genshin/s00 --n 8
python ae_shift_test.py --images data/10_frames/wuwa/s00 --n 8
```

| | 水平：k=1…31 均值 | 最低（k） | k=16 | k=32 | 垂直：k=1…31 均值 | k=16 | k=32 |
|---|---|---|---|---|---|---|---|
| 原神 | 27.35 dB | 26.61（11） | 30.48 | 43.93 | 27.25 dB | 31.99 | 40.89 |
| 鸣潮 | 27.98 dB | 27.25（11） | 32.04 | 44.52 | 28.25 dB | 33.55 | 43.03 |

k=1 就只有约 30 dB，k=2 起掉到 27–28 dB 的平台；曲线在 k=8、16、24 有小峰（k=16 最高），k=32（正好一个 token）回到 41–44 dB。结论：**DC-AE 在非整 token 平移下远非等变**，相邻相位的重建差异和重建误差本身同一量级，这就是经过 DC-AE 的闪烁下限。对路线的影响已写进 plan §8.1：teacher 必然有纹理游动，时序问题主要靠 student 阶段解决，student 绕开 DC-AE 又多了一条理由。曲线图在 `data/shift_test/{genshin,wuwa}_s00/curve.png`。"完整转换"那条曲线要等有了 pilot 模型再测（加 `--run`）。

### 5.3 阶段 1：离线过滤（plan §3.4、§3.5）

新写 `filter_frames.py`。按数据的实际情况调整了几处，都已写回 plan：

1. **全量 pHash 去重**：两边都是 0 张重复，在线的滑动窗口去重已经够用
2. **时段筛查**：先试了逐帧 CLIP zero-shot（P(夜或黄昏) > 0.5 就丢），看拼图发现边界上白天和夜晚的单帧得分混在一起，误杀和漏网都多，而且鸣潮偏冷的画风会被判成黄昏。按每分钟统计就很清楚：时段是采集时间的连续函数。于是改成**按整段时间排除**：会话目录下可以放 `exclude.txt`；没有时用 CLIP 得分沿时间轴的滑动中位数自动判（原神 s01 自动判出的边界和人工判读只差十几秒；鸣潮 s01 自动判会在夜里来回翻，所以人工写了）。按时间线拼图人工判读后写了三个文件：
   - `data/10_frames/genshin/s01/exclude.txt`：`11:13:12-11:26:27`（11:13 起黄昏，11:26:28 天亮）
   - `data/10_frames/wuwa/s01/exclude.txt`：会话开头到 `10:43:14`（10:43:16 起整体亮度从约 70 跳到 90 以上）
   - `data/10_frames/wuwa/s00/exclude.txt`：整个试采会话都是游戏内傍晚
3. **内容筛查**（CLIP：对话框 / 战斗 / 室内 / 特写的概率之和 > 0.5）：原神丢 5、鸣潮丢 2。抽检里还能看到少量带交互提示或小怪的帧，比例很小，没再收紧
4. **清晰度复核**：按计划原来的 10% 分位，原神阈值约 310，看被丢帧的拼图全是清晰的开阔草原（天空和平地多，Laplacian 方差天然低），只有最末尾几张是镜头贴进树丛、冰面水面特写。改成 3% 分位（阈值约 256），两边各丢 24、26 张
5. **固定叠加层掩码**：逐像素时域标准差 < 25 的像素（鸣潮的眼睛图标是半透明的，std 约 16–20，阈值 12 时漏检），两域取并集、闭运算、膨胀 3 像素。结果两个块：左上 (52,18) 起 26×21，右下 (895,560) 起 103×16，共 2075 像素（画面的 0.35%）

### 5.5 阶段 1：EDM 系数标定与 OT 配对（plan §2、§5.1）

新写 `sbflow/coeffs.py`、`sbflow/pairing.py`。

**合成数据自检**（单位方差高斯、随机配对，每个 ε 用 4096 对）：

| ε | τ=0.001 处 (c_in, c_skip, c_out) | τ=0.999 处 | 实测表与 §2.2 解析式的最大偏差 |
|---|---|---|---|
| 0 | (1.001, −1.000, 1.001) | (1.001, 1.000, 1.001) | 0.0005 |
| 0.05 | (1.001, −1.000, 1.001) | (1.001, 0.949, 7.145) | 0.0009 |
| 0.2 | (1.001, −1.000, 1.001) | (1.001, 0.798, 14.18) | 0.0020 |

和 §2.3 的验证值一致，偏差在蒙特卡洛噪声量级，说明 §2.2 的推导（含协方差项）是对的。

**真实配对**（RGB 代价、`ot_ratio` 0.8、16×16 窗口、ε=0.05，4096 对）：

| 项 | 值 |
|---|---|
| 方差 z0（原神）/ z1（鸣潮） | 0.715 / 0.589 |
| 均值 z0 / z1 | 0.046 / 0.081 |
| 配对相关 ρ（全部 / 只算 OT 那部分） | 0.255 / 0.269 |

随机配对也有 0.25 左右的相关，因为同一个 batch 共用裁窗（天空在上、地面在下）。正反向两张表差得不小：τ≈0.25 处 c_skip 正向 −0.62、反向 −0.42（解析式代入两域平均方差是 −0.53）；τ=0.999 处 c_out 两向都约 7.1。印证了"正反向各标定一张表"。

**OT 配对的效果**（每种设置 20 个 batch 的平均，代价越低越好）：

| 设置 | OT 配对的平均代价 / 随机配对 | 每 batch 耗时 |
|---|---|---|
| RGB，`ot_ratio` 0.8 | 0.0405 / 0.0661（0.61 倍） | 1 ms |
| RGB，`ot_ratio` 1.0 | 0.0409 / 0.0669（0.61 倍） | 2 ms |
| RGB，配对池 ×4 | 0.0398 / 0.0666（0.60 倍） | — |
| DINO，`ot_ratio` 0.8 | 0.633 / 0.750（0.84 倍） | 1 ms |

配对池放大 4 倍几乎没有增益：候选的多样性受数据量限制，而不是受 batch 大小限制。

- 固定集 val 比 train 高约 0.1 且差距缓慢变大：val 的地貌（鸣潮金色草地和岩石、原神的湖）和 train 不同，加上数据少。pilot 里要盯 `fixed/val_minus_train`
- 每步 186–200 ms；DiT-S 加面板的峰值显存 9.6 GiB

### 5.9 和原计划不一致、需要知道的地方

都已就地写回 plan（plan 只写现在的做法和理由，不写改动经过）：

| 项 | 原计划 | 现在 | 依据 |
|---|---|---|---|
| 时段筛查 | 可选的逐帧 CLIP zero-shot | 按整段时间排除：`exclude.txt` 人工判读优先，否则 CLIP 得分的滑动中位数 | §5.3 第 2 条 |
| 清晰度复核 | 两域各按 10% 分位 | 3% 分位 | §5.3 第 4 条 |
| 固定叠加层 | 没提 | 两域并集掩码，规范化时 Telea inpainting | §5.0、§5.3、§5.4 |
| val | 按会话：s05 + s00 | 过渡办法：从 s01 末尾切一段 + 45 秒保护带，有了 s05 再换回 | §5.3 第 6 条 |
| DINO | dinov2-small 或带 registers 的版本 | 配对用 small(registers)，评估用 base(registers) | plan §4.4、§7.2 |
| DiT | 没写 RoPE 频率、没有 QK-norm | 轴向 RoPE θ=10000；q/k 加 RMSNorm | plan §5.2 |
| EMA | 0.9999 | 0.9999 带预热 min(0.9999, (1+n)/(10+n)) | plan §5.3 |
| 采集协议 | 只写了 08:00–16:00 | 补了"原神游戏内一天 24 分钟，每 8 分钟调回早上"；采集指南同步更新 | §5.0 |

**还没做、但不挡阶段 3 之前的事**：`capture.py` 的 clip 模式和 warping error（都是阶段 4 的）；转换模型的平移等变曲线（要等 pilot 模型）。

**数据是现在最大的短板**：过滤后每域只有 500–600 帧训练数据（计划 3000–5000），只有草原丘陵一种地貌，val 也是临时切的。影响：
- 小数据上背图的风险更大，要盯面板里的 NN 指标和 `fixed/val_minus_train`
- 临时 val 两边内容不同（鸣潮 val 多是金色草地和岩石，原神 val 多是绿草地和湖），KID 的绝对值被内容差异撑大，不转换的 baseline 都在 300×1e-3 以上，只能在 run 之间横向比
- 冒烟测试里鸣潮→原神会把灰蓝的岩地画成绿草（§5.8），原神 train 里几乎没有岩地，OT 找不到对应的内容，这正是 plan §3.1 强调地貌配平的原因
